# State conventions template

Derived from runtime behavior in:
- `factories/mothership/graphs/factory_supervisor_tick.dot`
- `packages/capability-goal-decomposition/graphs/goal_run.dot`
- `factories/mothership/graphs/wave_dispatch.dot`
- `factories/mothership/graphs/wave_execute.dot`
- `hatch-ops`

Use this contract to keep state durable, queryable, and restart-safe.

## 1) Durable entity mapping (GitHub-backed)

| Entity | Canonical representation | Required metadata | Lifecycle |
|---|---|---|---|
| Goal | GitHub issue in `{{target_repo}}` | `goal`, `ready` labels; milestone linkage | open → decomposed/dispatched → closed |
| Wave | GitHub milestone (`goal-<n>-wave-<m>`) | title/number; open issue count | open → in progress → closed |
| Wave readiness marker | GitHub issue titled `Wave Ready: <milestone>` | `ready` label, milestone pointer | created → claimed/locked → closed/blocked |
| Work issue | GitHub issue in `{{target_repo}}` | priority labels, milestone, dependency links | open → implemented/reviewed → merged/closed |
| Infra bug | GitHub issue in `{{infra_issue_repo}}` | `bug` + factory metadata | open → remediated/routed → closed |

## 2) Ownership encoding (infra repo vs target repo)

Always encode ownership explicitly:
- `target_repo`: where feature/work issues and wave milestones live.
- `infra_issue_repo`: where factory design/runtime defects are tracked.
- `factory_repo`: where graphs, skills, and ops commands are versioned.
- `caller_identity`: actor/run metadata (`run_id`, `factory_id`, `wave_id`, `issue_number`) attached to state transitions.

Recommended context payload:

```json
{
  "factory_repo": "{{factory_repo}}",
  "target_repo": "{{target_repo}}",
  "infra_issue_repo": "{{infra_issue_repo}}",
  "caller_identity": {
    "factory_id": "{{factory.id}}",
    "run_id": "${__run_id}",
    "node_id": "{{node.id}}"
  }
}
```

## 3) state_snapshot contract used by outer-loop nodes

`state_snapshot` is generated by:
- `hatch-ops supervisor run --op state-snapshot --repo '{{target_repo}}'`

And augmented by:
- `hatch-ops supervisor run --op health-check --repo '{{target_repo}}' --run-id '${__run_id}' --pipeline '{{pipeline}}'`

Minimum fields to expose (additive allowed):

```json
{
  "ready_goals": [],
  "blocked_waves": [],
  "in_flight_waves": [],
  "infra_failures": [],
  "action_items": [],
  "health_state": "healthy|degraded|broken",
  "health_reason": "...",
  "capacity": {
    "max_concurrent_waves": 0,
    "available_slots": 0
  }
}
```

### Node-to-field usage map

| DOT node (template) | Required snapshot/health fields | Purpose |
|---|---|---|
| `snapshot_state` | all fields above | baseline state for this tick |
| `evaluate_open_bug_gate` | `infra_failures` or bug queue summary | fast-route infra defects |
| `detect_blocked_waves` | `blocked_waves`, `in_flight_waves` | prevent dispatch into stalled system |
| `list_ready_goals` / `goals_gate` | `ready_goals` | dispatch eligibility |
| `resolve_capacity` / `enumerate_slots` | `capacity.max_concurrent_waves`, `capacity.available_slots` | concurrency gating |
| `supervisor_review` | `action_items`, `health_state`, previous node outputs | next-step remediation/dispatch decisions |

## 4) Labels, milestones, and blockers

- Labels are state hints, not truth by themselves.
- Truth = issue/milestone state + deterministic command outputs.
- Use GitHub native blocking relationships (`blocked-by` / `blocks`) for dependency state, not ad-hoc labels.
- Wave markers (`Wave Ready: ...`) are control objects; close/block them through CLI commands, not manual edits.

## 5) Restart and crash semantics

- Treat `.hatch/runs/*/state.json` as ephemeral diagnostics.
- Durable truth must be reconstructable from GitHub + deterministic ops commands.
- Any tick should be safely re-runnable from entry graph with no manual state surgery.

## 6) Required command references in graph comments

Each template graph node that reads/writes state should include a comment pointing to one of:
- concrete source DOT node (for example `factory_supervisor_tick.dot:snapshot_state_fast`)
- concrete CLI command invocation (for example `hatch-ops supervisor run --op state-snapshot`)

This keeps template drift reviewable when production graphs evolve.
